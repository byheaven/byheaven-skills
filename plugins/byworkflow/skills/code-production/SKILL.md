# Code production

Before the first edit, decide whether the change adds or reshapes a type, a module, stored data, or a command or job that writes files or records. If it does, read [references/structure.md](references/structure.md) before shaping it.

Before the first repository action in a Git repository — install, build, test, check, or edit — follow [Shared checkout](../task-owner/references/repo-integration.md#applicability-and-boundary).

- In a Bun repository, use the shared `~/.bun` install cache (`~/.bun/install/cache`) with `bun install --offline`, setting `BUN_INSTALL_CACHE_DIR` to it when the environment points elsewhere. If it isn't writable, clone it copy-on-write (`cp -cR` on macOS, `cp -R --reflink=always` elsewhere) and point `BUN_INSTALL_CACHE_DIR` at the clone. Never do a fresh install into a private `/tmp` cache.
- Make the simplest coherent change that delivers a leading-finished-work result for the Intent; never trade quality for delivery speed, and define the highest standard across every applicable dimension before editing (premise/value truth, factual and third-party asset authenticity, audience/locale/ecosystem fit, craft, edge-case and runtime soundness, and locked intent) rather than deferring quality to QA or review. Modify or delete before adding; remove the superseded path in the same candidate. When an existing part the change builds on or ships is below standard, bring it up to standard or rewrite it cleanly—reporting the expanded scope after rather than patching over a broken foundation (asking first only for irreversible actions or boundaries a repository's own rules reserve)—without absorbing unrelated or concurrent work. The proportion of lines changed does not decide the method.
- Make code self-explanatory through naming, types, and structure, and place rationale, constraints, or API contracts in commit messages, PR descriptions, or documentation — never in source comments. Write **zero** explanatory, section, "why", or "do not remove" comments in source code. Keep only compiler/tooling-required machine directives (such as an intentional negative-type `@ts-expect-error`, `/* @vite-ignore */`, or `/// <reference />`) and legal/license headers; resolve lint issues in code rather than suppressing correctness or safety rules.
- Before handing over, read your own diff once as its reviewer and strip anything added without need: any explanatory comments, defensive checks or try/catch on trusted internal paths, casts that bypass the type checker, and nesting an early return would flatten.
- In a sweep, migration, or batch of similar edits, work so that a break shows at the unit that caused it. For such a batch, or a check you will repeat across many units, reuse an existing rerunnable command or script when one covers the work, otherwise write the smallest script that does or proves it, and keep the invocation as a receipt a reviewer can rerun; a couple of edits visible at a glance need none.
- Scope follows P1: within the user's scope allowance, widen it where the work calls for it and report the change with its reason; surface any other required expansion instead of silently crossing it. A pre-existing bug, performance concern, or adjacent improvement the directive does not mention is fixed in the same candidate when that allowance covers it, otherwise reported as a follow-up. Presentation, motion, feedback, and conventional states reach the highest craft the work allows (for web or interactive UI code, apply [web-craft.md](../experience-design/references/web-craft.md)). What the invariants of the [Product decision gate](../task-owner/references/experience-gate.md#product-decision-gate) return to the owner stays out and is reported as a gap.
- A repository's written testing standard adds to the rules below, never weakens the ban on self-confirming or meaningless tests.
- A new test needs an expected outcome from outside the code it checks; a test written from the same reading as the implementation repeats that reading. Three sources supply one. A **bug**: the fix starts with a case that fails on the unfixed code for the reported reason. A **decided requirement** that predates the change: each case asserts an outcome its statement names. A **trust boundary** (authentication, money, deletion, privacy, or a guard on production or secrets): independently derived adversarial cases stay required. Every other change adds no test and runs the existing checks that cover it.
- Test behavior through the public interface, at the seams the directive or Intent names. A self-confirming or restating test is a defect, not coverage — never add one: a fake external-protocol mock asserting the author's own outgoing request payload or invented upstream response against a mocked `fetch` or upstream client, a copy of a value the code already holds (a count or roster from a registry, copy text, prompt wording, a constant, source or script text), a test asserting only that a mock was called, or one recomputing the expectation the way the implementation does. A check over every entry of a registry enumerates the registry. When an intended change breaks a restating test, delete or rewrite it rather than update its copy. When a module deepens behind a new interface, delete the superseded shallow tests in the same change. Size committed tests like the neighboring test files, roughly one focused test per stated behavior; scratch checks used during verification need not be kept. A committed test runs production code or checks a formal structure such as a schema, path, heading, link, or size; a one-time observation, such as a deleted file being absent, belongs in the result's evidence.
- Run the smallest checks that directly judge the changed predicates. Broaden to regression or build coverage when the actual impact surface or dependency uncertainty requires it, and repeat or broaden passing checks only when new changes, failures, or unresolved concerns justify it. Record exact command, exit or result, and raw output location when available. Silence, timeout, malformed output, or a skipped check is not a pass.
- For a performance change, where speed, latency, memory, size, frame rate, or cost is the target, read [references/performance.md](references/performance.md) before the first edit and follow it through the report.
- A domain skill you load does not widen scope or change Acceptance.
- A wait you own — a probe still scanning, a check or deploy still running, a process you started — belongs to this change: stay with it until it reaches terminal state or its stated bound, then report.
