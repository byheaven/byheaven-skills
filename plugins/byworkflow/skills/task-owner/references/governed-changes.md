# Governed changes

Before adding, changing, or removing a rule, default, constraint, or agent definition, read the Human-Agent Principles and the applicable project Vision through its project entry. Collaboration-method mechanisms derive from the Vision of the project that owns the method; an affected project's product commitments retain that project's own authority. When the change is text an agent will follow, its outcome is that it holds to P3's Methods: every constraint it adds or keeps carries the user's decision or guards a concrete risk, and nothing in it holds the model below its full capability. Each changed file also repeats nothing another file states and states its key requirement first, and every other current text the change supersedes or contradicts (plugin files, deployment rules and bindings, scripts, sibling project entries, competing carriers) changes in the same candidate; the `writing-for-agents` skill gives the method. When the change is a writing task as the `content-creator` skill defines it, such as a Vision, load that skill and follow it: write and check the brief, draft, then give the user both for one review. Reuse current context and existing execution authority.

Derive the protected outcome from those foundations, with current evidence as the reference that tests it. Distinguish a durable requirement from a conditional method or a patch for an observed capability gap. Apply P3 to necessity and scope: explain the observed gap, why existing or simpler means are insufficient, and which conditions make the method useful. A real simpler sufficient case narrows a proposed universal method. Within settled bounds an executing agent may choose an alternative supported by qualified evidence of the same protection; confidence, lower cost, or a model announcement alone does not establish equivalence. Keep material rationale in the existing task or result, without a separate admission form.

A temporary capability patch names its observed gap, outcome probe, review point or expiry, executable exit action, and the protected requirement that survives removal. At that point, use the evidence to keep, narrow, replace, or remove the patch. Insufficient evidence names the missing observation and next bounded trigger; expiry alone never drops a required protection. Use the existing task or observation record rather than creating a separate patch registry or scheduler.

Locate the decisions and consumers affected by the rule. Establish how each receives the authority before its decision, following the directive contract in [Topology](production.md#topology). Preserve historical references as clearly labeled pointers where needed. Assign changed or unproven loading and application predicates through [evidence.md](evidence.md), reusing still-valid evidence. A canonical file, link, or syntax pass alone does not prove runtime activation or correct application; unobserved paths remain unknown. If the project defines an improvement or learning method, read its applicable branch before choosing a change to that method.

Use qualified independent judgment (the `verifier` agent) on a high-risk change's semantic scope, conflicts, necessity, and equivalent revivals. Machine checks enforce formalized schema, enums, paths, structure, transitions, reachability, and state binding; prose classifiers, regex, embeddings, and automated LLM scores do not establish semantic equivalence, completeness, or quality. User-owned foundation changes remain under P1.
