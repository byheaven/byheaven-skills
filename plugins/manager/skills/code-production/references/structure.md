# Structure

Read before a change that adds or reshapes types, state, module boundaries, or an operation that changes persistent state. Each point is a judgment for this change, not a refactor of surrounding code.

- **Data shape first.** Name the core types and the ways they are read before writing logic. When a concept has variants or a lifecycle, model it as one structure — a state machine, a discriminated union, a lookup table — so a new case is a new entry. A feature that adds one more branch to an existing if/else chain, or a second flag that must stay in sync with the first, is the sign the structure is missing.
- **Redesign for the new requirement.** When a requirement changes what the design assumes, shape the code as if it had been a premise from the start instead of attaching it beside the old shape, and carry the change through every reference: types, callers, docs, and examples.
- **Keep the reader's load small.** Count the layers a reader passes between a question and its answer and the hidden or mutable state they must hold in mind. Inline a pass-through layer that carries no meaning, protocol, or state boundary of its own and whose removal leaves the code easier to follow, prefer returned values to shared mutation, and add a layer or piece of state only when it removes at least as much load elsewhere.
- **Validate at the boundary.** Parse input that crosses a system boundary — command-line arguments, configuration, network responses, files other processes write — once, into typed data. Inside the boundary, trust that data and let errors propagate. Keep decisions in pure functions the thin shell calls.
- **Converge on rerun.** A step that changes persistent state reads the current state, compares it with the goal, and applies only the difference, so running it twice, or after a crash at any point, ends in the same state. Anything it leaves behind — a lock, a temporary file, a half-written record, a claim — is recognizable as stale by the next run from evidence that holds wherever the previous run stopped.
- **Separate writers before locking.** When concurrent actors might write the same file, key, or branch, first give each its own target and merge at the read side. Serialize with a lock, sequential phases, or a single owner only when one shared target is a real invariant; a written convention does not stop a concurrent write.
- **Design for the next agent.** Assume the next contributor sees only the files it opens, copies the nearest example, and takes the shortest path that compiles. Prefer the shape where a change that looks right from one file is right for the whole repository: one owner per piece of state, one supported way per task, internals the wrong import cannot reach.
- **Commit order as argument.** Order commits so the sequence proves the change: a failing test before its fix, a removal before the reshape, a baseline before the treatment, the scaffold before the feature.
