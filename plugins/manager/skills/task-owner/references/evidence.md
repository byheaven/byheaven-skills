# Evidence assignment

P2 in the [principles skill](../../principles/SKILL.md) owns judging capability, evidence scope, independence, and proportionality to risk and recoverability. This procedure maps those requirements to acceptance predicates and carriers; it sets no separate evidence standard.

## Owner acceptance

Owner acceptance is the exhaustive closure of objective Acceptance evidence before any completion claim, terminal write, or completion-stage request for user judgment. Re-read every locked Acceptance predicate and bind each to the exact candidate state, target environment, representative stored or input state, true judge, and current evidence. An interim experience review first closes only the objective prerequisites needed to judge its version-bound object; final acceptance still closes every objective predicate. The task owner obtains, reads, and evaluates that evidence; the user is never its test carrier or evidence collector. User judgment is the true judge only for a predicate irreducibly about value, taste, risk, or irreversible authorization, and returns to the user only after every objective predicate is current. External visibility, private browser or account state, and missing tool access do not transfer an objective predicate to the user: the task owner obtains the necessary access or authorization, or leaves the predicate unknown and the task owned and in progress.

Assign evidence per locked Acceptance predicate, never per file, batch, phase, cost tier, or artifact label.

1. Write the predicate and concrete artifact state.
2. Name the true judge: deterministic machine, external live authority, independent judgment, or the user only for an irreducibly user-owned predicate. A **high-risk** predicate — about authentication, money, deletion, privacy, or an irreversible action, or one that materially changes a Vision or adds, changes, or removes a rule, default, or constraint — always has an independent judge, from another model family by default and with no blind-spot reason required; the judge is same-model only when no cross-model carrier is available, and the [report](../SKILL.md#report) names that gap. Any other predicate whose true judge is independent judgment gets its judge from another model family by default in the same way. Some predicates outside the high-risk class need no independent judge, whatever files they touch:
   - documentation and records that no agent follows as a rule, such as READMEs, changelogs, task records, and research notes;
   - a correction that changes no meaning;
   - a mirror that a hash proves identical to its source;
   - version metadata;
   - a repair to a test's path.

   The producer's own check and the deterministic evidence that covers it close each of these. For authentication, money, deletion, or privacy, that judge derives acceptance cases adversarially from the locked Acceptance without seeing the implementation; those cases are the locked source its step-3 carriers assert.
3. Obtain and evaluate the judge's cheapest state-bound evidence that adds information. Expected outcomes come from the locked predicate or its authority, never from the implementation. Establish that the check can distinguish the required outcome from a relevant failure. New or changed tests, bug reproductions, uncalibrated methods, and high-consequence claims require evidence for their changed or unproven judging power. Prefer an observed failure of the behavior's own assertion on a subject lacking it: the comparison base when meaningful, otherwise a named change to the exact subject. When that method cannot meaningfully judge the claim, qualified alternative evidence must demonstrate the same discrimination and name its authority, observation, and limits; rationale or green alone is insufficient. Reuse still-valid calibration rather than manufacturing a new red on every run.

   A stand-in limits evidence to the real layer actually exercised; its location inside or outside the repository does not decide validity. A simulated dependency or injected fault may support the real consumer's response, but cannot establish the substituted logic, real persistence, permissions, external exchange, or complete chain. A test-defined replacement model does not prove production behavior. A red caused only by reworded prose is not a missing behavior: document meaning goes to a qualified reader; tests judge formal structure. A one-time observation such as a deleted file's absence is terminal evidence rather than a committed test. Missing judging-power or observed-layer evidence leaves the affected claim unknown.
4. Identify the locked commitment being judged and the exact artifact state that realizes it. The judge named in step 2 decides dispatch: a deterministic machine or live authority closes the predicate with no further verifier; an irreducibly user-owned predicate returns to the user once every objective predicate is closed; independent judgment means one fresh verifier, or a parallel wave, is the judge, and the task owner's own reading never closes that predicate.
5. Missing, empty, malformed, refused, timed out, non-zero, pending, stale, or wrong-state evidence is unknown and blocks completion until it is settled or closes under [Predicate closure](#predicate-closure).

Terminal evidence names each predicate's judge and, for independent judgment, the verifier's model family, so a later audit can check the assignment. A claim that a change is safe, or leaves something unaffected, states the strongest level its deciding fact reached: asserted, located at a cited line, failure path walked through, shown by running the real code, or reproduced in the running product. User judgment and irreversible authorization are never delegated, and neither substitutes for owner acceptance. File paths do not decide semantic adequacy, true-judge assignment, or verifier need.

## Predicate closure

Each predicate closes as **confirmed**, **refuted**, or **unjudgeable**. For each, check whether the carrier replaced the predicate's named layer — or, where Acceptance names none, the layer the outcome rests on — with a stand-in; a green carrier proves only what it can directly observe. A refuted predicate blocks completion until repair or reopened Direction settles it. An objective unknown keeps delivery in progress and owned while the task owner obtains evidence, access, or necessary authorization; the user is not its fallback test carrier.

A predicate turns unjudgeable only after that attempt fails because its judging layer is unreachable from this task at all, and only in three cases: users who do not exist yet, an external gate outside the work, or an authorization the user has already refused. It then names the missing layer, what was attempted, and the observation that would settle it. A predicate this user can judge now is never unjudgeable. A delivery with no refuted predicate, whose every unclosed predicate is unjudgeable, completes, carries them in its terminal evidence, and names them in the evidence the [report](../SKILL.md#report) links.

Only a remaining irreducible value, taste, risk, or irreversible-authorization predicate keeps a blocking completion gate with three answers: done, needs adjustment, pause. External visibility or a governance surface alone does not create that gate. "Done" closes only the remaining user-owned judgment; it never replaces objective evidence. "Needs adjustment" continues Delivery and reopens Direction when needed. "Pause" records the user's explicit instruction and releases the task's ownership; work resumes only on the user's explicit resume. A reversible delivery with complete state-bound evidence and no remaining user-owned predicate may complete asynchronously; blast radius changes the evidence demanded, not who performs objective acceptance. Silence, external dependencies, resource waits, and timeouts keep the delivery in progress and owned.

An effect only later real use can show — including one awaiting users who do not exist yet — is never a predicate of the delivery; a locked delivery predicate of that kind moves out only through reopened Direction. Direction names it with its refuting observation and the keep, adjust, and withdraw conditions, and the project's task store carries it as a separate observation scheduled for the earliest date the evidence can exist, if the store supports one; otherwise record it in the evidence the [report](../SKILL.md#report) links.

A defect known to have reached a user or production cannot complete until its escape has been diagnosed and classified, using a bug-diagnosis skill if one is installed, and its classification is carried in the terminal evidence.

The escape is also a **review replay case** when a reviewer of the change that introduced it, holding that change and the Acceptance it was judged against, could have reported it, whether or not a verifier ran. Record each such case in the review replay set where the user's or the project's instructions place it, starting from the first escape after those instructions exist: the reviewed state, precise enough to restore exactly; the directive or Acceptance the review had; the defect a reviewer should have reported, with its location; and what any verifier said about it. When no location is named, the evidence the report links carries the case instead.

## Evidence reuse

Evidence reuse is decided per predicate and judged layer across candidate, base, build, and release changes. Reuse requires evidence that every relevant input and observation condition remains unchanged, including dependencies, configuration, tooling, and runtime or external state where the predicate depends on them. An unchanged file or author revision alone is insufficient; unknown relevance requires fresh observation of the affected predicate.

Across a rebase or base update, equal `git patch-id --verbatim` values for the judged change range, computed on the reviewed commits and on the new ones, are the receipt that the change's own content is unchanged; an independent verdict then carries only for a predicate whose other relevant inputs the base change leaves unchanged, and the composed result is observed on the new head by its deterministic carriers. Differing values, or a reviewed range no longer reachable, leave the change content unproven.

At a release boundary, close every predicate decidable on the exact candidate, release that same artifact, and carry its still-current receipts forward; they stay valid when bound to the exact tested artifact and the release neither replaces nor transforms the layer the predicate rests on. After release, remint only predicates invalidated by a deployment transformation, and add predicates only the target environment can expose, such as deployed-artifact identity, routing, cache behavior, runtime bindings, migrations, permissions, or external authority. A repeated product-behavior probe names the concrete deployment risk it observes. When exact artifact identity is unavailable, or build or runtime injection can change the behavior, the affected predicate is invalidated and observed again.

## Verifier dispatch

Production files, batches, phases, topology choices, and intermediates are not evidence boundaries. A commitment identity names the locked promise being judged, the Intent or the Acceptance slice under review, apart from the artifact states that realize it: a repair inside the same locked Intent and Acceptance keeps the identity, and a change to what is promised is a materially new commitment. Every selected verifier receives the same locked commitment identity and exact artifact state in a provenance-isolated directive, plus authority or spec, Acceptance and scope, the approved writing brief and approved review object the producer worked to where they apply, and current receipts, but not producer reasoning. When a predicate judges what the user decided, the user's own words are the authority: quote them verbatim with their date and place, and give any producer-written proposal the user replied to only as producer-written text. Agreement to a whole proposal is recorded as given and confirms none of its individual items. Because a verifier cannot load this skill's references, the directive carries the excerpts it needs, such as this file, and always [Governed changes](production.md#governed-changes) when the artifact adds, changes, or removes a rule, default, constraint, or agent definition, and the [global-rules excerpt](production.md#topology) when the verifier does not load the user's global rules; for a plan costly to reverse it carries the failure question from [Before a plan settles](direction.md#before-a-plan-settles). A wave is justified only when distinct specialist capability, observation method, or model-family blind-spot exploration adds information or shortens the trustworthy path; never partition it mechanically by Conformance, Coherence, and Soundness. Carrier selection, including any cross-model carrier, does not alter scope, independence, or judgment. Each verifier may explore any relevant evidence and challenge the target or architecture premise, but cannot rewrite Direction or authorize modification. Every finding names its severity (critical, high, medium, or low), the real scenario, evidence, impact, relationship to locked Intent or Acceptance, and the smallest sufficient repair; the task owner joins all findings once, giving each a stable id that a follow-up case cites, and decides whether the evidence reopens Direction.

Settle every finding from each join as exactly one resolution: **fixed** when the artifact changed because of it; otherwise **wrong** (it is false), **intentional** (it describes a locked decision or deliberate behavior), or **immaterial** (true, but not worth a change). A finding under repair settles as fixed when its repair lands, and one returned to Direction settles when Direction decides. Append one row per settled finding to the verifier finding ledger where the user's or the project's instructions place it: date, project, delivery, verifier model family, severity, the finding in a few words, and its resolution. The terminal evidence carries the count of each resolution; when no location is named, the evidence the report links carries the rows instead.

After the verifier or wave joins, integrate supported findings and remint only invalidated predicates through their true judges. A delivery gets one review round by default. A repair to a finding the verifier marked fully specified, applied as prescribed, closes once the task owner checks its diff against that prescription. A medium or low finding is fixed, or given its resolution, without another round. Assign a bounded independent follow-up only in two cases: a critical or high finding remains unresolved, or a repair changes behavior beyond its prescribed fix. The follow-up covers that question and its affected dependency closure at the repaired state, and may use the original or a fresh qualified judge. A follow-up directive opens with `Follow-up case: <finding id> unresolved critical/high` or `Follow-up case: repair <finding id> exceeds its prescription`, judges only that case and its affected dependency closure, and names no other finding. Even when fully specified, a repair that re-points references, aligns with another artifact's change, or fixes a test closes on a deterministic check (grep, test run) plus the task owner's diff check. A gate or deadline is stated as `no open critical or high finding on <object>`, never as an approve verdict. After two follow-ups on one delivery, stop and return each open question to the user to decide. A changed file or new PR revision alone does not justify repeating the complete review. Each follow-up needs a named unresolved question and new state or evidence, so unchanged repetition cannot become a review loop. Task-owner confidence never closes an open independent semantic predicate. A materially new commitment gets a fresh need assessment; a remaining material unknown blocks completion until settled, judged unjudgeable, or returned to Direction when a user-owned dimension changes.

## Producer-routed verification

The task owner may delegate this route in a producing worker's directive. The directive carries the delivery requirements, the locked commitment and its identity, and the fields and excerpts [Verifier dispatch](#verifier-dispatch) requires, including the approved writing brief, approved review object, and [Governed changes](production.md#governed-changes) excerpt where applicable. It states whether verification is mandated and names the verifier endpoint for the route as the deployment's binding maps it, the producer the endpoint returns repairable findings to, and how long the endpoint waits for a repaired state. The route delegates artifact forwarding, not sub-agent creation. An artifact the task owner produces itself is outside this route: the task owner classifies it and dispatches any verifier under [Owner acceptance](#owner-acceptance) and [Verifier dispatch](#verifier-dispatch).

Before delivery, the producer classifies each predicate under [Owner acceptance](#owner-acceptance) step 2: name the predicate, its class, and the concrete fact placing it there so the call can be checked. High-risk predicates always require verification. Exemption requires everything in the artifact to fall within step 2's exempt list; any other predicate whose true judge is independent judgment requires verification. When unsure, or when the directive mandates verification, verify.

- **Verify.** Send the exact artifact state directly to the named verifier endpoint with the directive's fields unchanged, the producer's model family, and the task owner to receive the findings and final verdict; include no producer reasoning. For code, the exact state names the repository root, commit SHA (pull request head), and comparison base. The verifier selects its model family under step 2. It runs as [Verification carrier](runtimes.md#verification-carrier) requires. The verifier endpoint runs the one repair round below, then returns all findings and the final verdict to the named task owner, which joins and settles the findings under [Verifier dispatch](#verifier-dispatch) and assigns any further repair.
- **Repair round.** When the verdict needs attention, the endpoint sorts each finding before returning. A finding about scope, direction, or what the Acceptance should be goes to the task owner, and one about taste, such as copy tone or whether a design looks right, goes to the task owner marked as the user's to decide. The endpoint sends the rest straight to the producer to repair once, inside the original directive's bounds, then pins the repaired state as it pinned the first. It re-verifies, with the same verifier model and charter where they can run, only a follow-up case under [Verifier dispatch](#verifier-dispatch); every other repair returns marked for the task owner's diff check. When the producer is unreachable, or no repaired state arrives within the directive's wait (24 hours when it names none), those findings return to the task owner as open; a timeout is never a pass. Every finding returns with its state after the round: open, repaired and re-verified, or repaired awaiting the diff check. A second round runs only when the task owner assigns a follow-up case. When the endpoint cannot reach the producer at all, it skips the round and the task owner assigns repair.
- **Exempt.** Deliver to the task owner marked `not verified: <class>, <predicate and classifying fact>`, with the producer's check and deterministic evidence required by step 2.

Record every route choice with its classification and reason where the user's or the project's instructions place it, otherwise in the evidence the [report](../SKILL.md#report) links. The task owner retains acceptance, deciding whether the classification holds, joining and resolving findings, assigning follow-up rounds, and merging; it may still send an unverified artifact to a verifier at acceptance.

Independence holds because the producer forwards fixed fields only, never selects, briefs, or judges its verifier, and the verifier starts fresh without producer reasoning.

## Failure diagnosis

When a predicate fails or a defect recurs, diagnose the cause before choosing the next action. Distinguish a changed or unsatisfiable commitment, an implementation defect, an environment or infrastructure fault, stale or invalid evidence, and a correlated reasoning failure. Repair or obtain missing evidence within settled Intent, Boundary, and Acceptance. Reopen Direction only when the remedy changes a locked user-owned dimension; failure count and an environment defect alone do not establish that change.

When two fixes resting on the same premise have failed the same check, write that premise down and test it directly with an observation that would come out differently if it were false, looking at how the failures are distributed as well as how large they are, before a third fix assumes it. An unchanged failed approach is repeated only with new evidence. Choose the smallest sufficient corrective action from the diagnosis, which may include an environment repair, a different implementation, or a fresh candidate produced from Intent and joined findings. A materially new commitment receives a fresh judge-need assessment under step 4; changing context alone neither guarantees correctness nor waives evidence. If the cause remains unknown, keep the affected predicate open and pursue a discriminating observation or report the exact blocker. External retries and waits remain bounded.

Semantic rule conflicts and equivalent revivals go to the `verifier` agent. Machine checks enforce only formalized contracts.

## Dependency waits

Before repairing a blocking fault, inspect its live repair record and runtime or execution process. A PR or task record alone is not evidence that another agent is executing. If another agent is repairing it, defer that repair, keep this task owned and in progress, and arm a runtime-supported automatic wait that resumes this same conversation. Bind the wait to the dependency's observable terminal result, a deadline, and the next action; confirm the wake mechanism is registered before ending the turn. A snapshot, a prose "next step", or a detached process without a wake signal is insufficient.

On dependency success, verify the result at its live authority and continue this task through its remaining checks, integration, and acceptance under the existing authorization. A repair's completion alone does not complete the dependent task. Re-arm automatic continuation at each later external wait. Stop it when the task completes, the user pauses or cancels, or a necessary user-owned decision is reached. Each wait has a bounded lifetime under [External waits](../../principles/SKILL.md#external-waits); timeout or repair failure wakes the task owner to diagnose and act, never to mark success or silently release ownership. Unchanged state stays quiet; surface a material failure, timeout, or required user action. Retry only when fresh evidence supports another bounded attempt.

If no agent is executing the repair, diagnose the fault, state the simplest concrete repair plan, and carry it out within current authority. Scope, value, risk, and irreversible choices go back to the direction owner under [Handoff](direction.md#handoff), and repository effects follow the repository authorization rules; request only missing authority after reversible preparation. A stopped or completed repair is re-evaluated through this branch, preserving its existing work and ownership safeguards.
