# Production topology and integration

One task owner keeps the locked Intent and Acceptance and owns integration continuously from the start of Delivery through completion.

For code editing, apply the `code-production` skill whether the task owner or a sub-agent produces the change; this imports editing and checking methods, not the sub-agent's ownership or lifecycle boundaries. For anything a person experiences in a product, apply the `experience-design` skill to its design, text, and review in the same way. Repository commit and integration follow [repo-integration.md](repo-integration.md).

## Topology

The task owner chooses self-production or a bounded dispatch under P3's hand-off reasons in the deployment's always-loaded rules. Accountability stays with the owner: another writer is an execution choice, not a transfer of the Goal, Acceptance, or integration. A worker charter is optional when a focused directive and the applicable method skills supply the whole slice. A taste- or design-load-bearing commitment uses [Design rounds](design-rounds.md).

Concurrent writers need locked shared authority and interfaces, bounded Acceptance slices, and disjoint write surfaces, including any judge that modifies an artifact to test it. Unresolved interfaces, overlapping writes, and dependent slices stay serial. Dispatch only with a result route that resumes the owner; end the turn after any remaining independent work instead of waiting in-turn. A sub-agent creates no task state, integrates no peers, and spawns no sub-agents.

**Directive.** Every directive opens with the 1–3 checkable outcomes its slice must reach; a bare instruction to load a skill is not an outcome. Every producer or investigator receives a focused directive containing: the larger task and who it serves; the locked objective; its bounded Acceptance slice, stated as behaviors to judge, not as tests to write, or concrete question; relevant authorities, interfaces, and current facts; the exact write boundary (for repository work, the worktree and branch it commits and pushes to); and the result contract. For a task-specific constraint, name the decision it governs, its source and section, and when to read it; carry settled boundaries directly and reuse current context. A fresh sub-agent inherits neither the task owner's reads nor linked files, so the directive carries the excerpt of any task-owner reference the sub-agent needs, such as [Governed changes](governed-changes.md). **Global-rules excerpt.** Any directive, packet, or hand-over sent to a session that does not load the user's global rules (a producer, investigator, verifier, derivation route, or one-shot CLI run) carries what it needs from them, as the deployment's generated excerpt file where one exists: P1–P3 and the applicable Project foundations and Memory and Rules duties from the deployment's always-loaded rules, reply language, every applicable floor, and that questions return to its dispatcher, never to the user. Select a role whose charter supplies the needed reading triggers, and prescribe only reading the task needs. For a user-visible surface, the directive carries the approved review object itself or a reference to it; copy, states, and entry points come only from that object or from [experience-gate.md](experience-gate.md), never from the task owner's paraphrase, and craft within its direction follows the direction invariant there. The parent transcript and peer work stay outside the directive. Raw payloads stay at stable receipt locations; the sub-agent follows them only when exact observation is needed.

**Runtime.** A same-runtime sub-agent receives the runtime-native directive, uses that runtime's agent configuration, and reports through the native result channel. The model and reasoning effort every producer, verifier, and derivation route runs, and the fallback when one is unavailable or out of quota, come from the deployment's model routing when the user's instructions name one; the runtime's configuration supplies only the invocation. A shape commitment Direction left open (a module boundary or interface others depend on, a stored-data shape, or anything costly to reverse) starts from the README-style usage and two or three real call sites, then the types derived from them; bring in a producer from another model family for a [competing candidate](design-rounds.md#competing-candidates) only when it would likely change the choice. Cross-runtime or cross-model production needs a P3 hand-off reason; a high-risk predicate's judge is cross-model under [Owner acceptance](evidence.md#owner-acceptance). A second runtime is never generic capacity or a full-native-slot escape. Justified cross-runtime production uses its configured carrier; review follows [Verification carrier](runtimes.md#verification-carrier).

## Re-evaluation

On every material result or authority or interface change, re-evaluate each pending and active sub-agent against its locked premise, Acceptance binding, and expected remaining value. A pending one that remains valid stays eligible; an active one that remains valid and valuable receives only the newly relevant facts. When the premise becomes invalid or remaining value no longer justifies the work, skip dispatching it, stop it, and reject its result from integration. A foundational Direction, shared-authority, or interface change applies the same rule to every affected sub-agent; dispatch a fresh bounded slice from the new authority only when work remains valuable. An unaffected sub-agent continues only when the update provably leaves its assumptions, write scope, and Acceptance binding intact; followups that preserve invalid context are not continuation.

## Integration

The task owner integrates every topology into one candidate. At a join, consume only distilled findings and stable references to raw receipts; retrieve exact evidence only when integration or judgment needs it. Files, batches, plan steps and drafts are not deliverables. Merge adjacent outputs before the next commitment boundary. During production, run targeted checks mapped to changed predicates. When artifact state and write permissions permit, independent deterministic closure such as consumer audit, architecture-document reachability, projection freshness, runtime smoke, and test shards may run concurrently and join once. Broaden to full regression only when the actual impact surface or dependency uncertainty requires it. Where the workspace maintains a behavior-assertion registry for its user-visible surfaces, run the registered executable carriers — end-to-end included — of every surface the delivery touched after integration and before owner acceptance, unless the project names its own decisive check for those surfaces, which then governs; a red carrier is repaired in-task through the repair-now route. Capture an independent candidate-state list only when drift risk across repositories, runtimes, artifacts, concurrent writers, or a long wait makes the observed state otherwise ambiguous. Neither is a fixed closeout step.

Evidence is assigned, preserved, and reminted per predicate under [evidence.md](evidence.md). When independent semantic judgment is warranted, identify one locked commitment identity and exact state, then select one verifier or a parallel wave divided by real specialist capability, observation method, or model blind spot. Join the one review round, then settle its findings under [Verifier dispatch](evidence.md#verifier-dispatch). Rework on a dispatched writer slice resumes that writer's session (its worktree for code) with only the findings to fix; only when resuming is unsupported or fails does a fresh run get the original directive and the open findings. Resolved parts are not replayed without invalidation. A materially new commitment gets a fresh verifier-need assessment. Unknown remains open until settled, judged unjudgeable under [Predicate closure](evidence.md#predicate-closure), or returned to Direction when its bounds change.
