# Production topology and integration

One Manager keeps the locked Intent and Acceptance and owns integration continuously from Direction through delivery.

For code editing, apply the `code-production` skill whether Manager or a sub-agent produces the change; this imports editing and checking methods, not the sub-agent's ownership or lifecycle boundaries. Repository commit and integration follow [repo-integration.md](repo-integration.md).

## Topology

Manager delegates for two bounded purposes: trustworthy wall-clock scheduling and context isolation. For scheduling, it uses parallel-first scheduling for currently ready work, not parallel-first decomposition. It chooses among self-production, one producer, and parallel producers by expected information gain, specialist value, context-pollution risk, shared authority and interface maturity, producer-correlation risk, integration cost, and the trustworthy critical path that determines wall-clock time to completion. Dispatch overhead and repeated context are integration costs; token duplication alone is never a veto against useful parallel work. Prefer shorter bounded slices when they can integrate independently and shorten that path; retain a broad owner when splitting adds more dependency or integration cost than wall-clock value. At each dependency layer, dispatch every currently ready slice eligible for parallel production in one wave whenever this is expected to shorten trustworthy wall-clock time, then join once. Keep eligible work serial only when current runtime capacity or handoff and integration cost removes the expected gain, and record that reason in the transient plan. When no wall-clock gain remains but an investigation would materially pollute Manager's integration view, dispatch a bounded read-only investigator if isolation value outweighs its handoff and join cost. Otherwise keep the work with Manager. These are topology judgments, not wave, time, fan-out, round, or slice-count quotas.

Delegate an independent subtask when it can run behind a locked shared interface and Manager can keep working while it runs; dispatch a verifier whenever a semantic predicate needs an independent judge. One producer is appropriate when a coherent surface benefits from specialist ownership or separation. Parallel production is legal only after the shared authority and interface are locked, each sub-agent has a bounded Acceptance slice, and write surfaces are disjoint; that last condition binds every concurrently dispatched agent that writes, including a judge that modifies the artifact to test it, because a peer reading the shared surface takes that modification for the candidate. Work with an unresolved shared interface, overlapping writes, or dependency on another sub-agent's result stays serial. A sub-agent creates no task state, integrates no peers, and spawns no sub-agents.

**Directive.** Every producer or investigator receives a focused directive containing exactly: the larger task and who it serves; the locked objective; its bounded Acceptance slice or concrete question; relevant authorities, interfaces, and current facts; the exact write boundary (for repository work, the worktree and branch it commits and pushes to); and the result contract. For a task-specific constraint, name the decision it governs, its source and section, and when to read it; carry settled boundaries directly and reuse already-current context. Manager's reads do not transfer into a fresh sub-agent, and linked files are not automatically loaded, so the directive carries the excerpt of any Manager reference the sub-agent needs, such as [Governed changes](#governed-changes). Select a role whose charter supplies the needed reading triggers, and prescribe only reading the task needs. For a user-visible surface, the directive carries the approved review object itself or a reference to it; copy, states, timing, motion, and entry points come only from that object or from [experience-gate.md](experience-gate.md), never from Manager's paraphrase. The parent transcript and peer work stay outside the directive. Raw payloads stay at stable receipt locations; the sub-agent follows their references only when exact observation is needed.

**Runtime.** A same-runtime sub-agent receives the runtime-native directive, uses that runtime's agent configuration, and reports through the native result channel. Cross-runtime or cross-model production is justified for a new architecture commitment that specifically benefits from model-family-independent challenge, Acceptance that explicitly depends on model-family-independent information, or necessary specialist capability unavailable natively; a high-risk predicate's judge is cross-model by default under [Manager acceptance](evidence.md#manager-acceptance) step 2. A second runtime is never generic capacity or a full-native-slot escape. Justified cross-runtime work uses the runtime's configured cross-model carrier, if any.

**Competing candidates.** For a taste- or design-load-bearing commitment, N independent candidates for the same target surface may be drafted concurrently, each on its own disjoint scratch surface without shared drafts, followed by exactly one selection. Candidates never co-write the shared target; only the selected candidate is integrated. Use this when output variance is high and the predicate's judge can rank real samples; mechanical work with one correct shape stays single-candidate. When user taste owns the standard, the user picks among real samples delivered asynchronously while Manager continues selection-independent work; when the standard is objectifiable against a named authority, a multi-perspective judge panel picks and its ranking rationale is kept with the delivered state. The selected candidate — optionally grafting a cleanly separable strength from a loser — enters the ordinary integration and evidence path. Losing candidates leave the integration path; retain only useful comparative evidence in the project's research or learning record, if any.

## Re-evaluation

On every material result or authority or interface change, re-evaluate each pending and active sub-agent against its locked premise, Acceptance binding, and expected remaining value. A pending one that remains valid stays eligible; an active one that remains valid and valuable receives only the newly relevant facts. When the premise becomes invalid or remaining value no longer justifies the work, skip dispatching it, stop it, and reject its result from integration. A foundational Direction, shared-authority, or interface change applies the same rule to every affected sub-agent; dispatch a fresh bounded slice from the new authority only when work remains valuable. An unaffected sub-agent continues only when the update provably leaves its assumptions, write scope, and Acceptance binding intact; followups that preserve invalid context are not continuation.

## Integration

Manager integrates every topology into one candidate. At a join, consume only distilled findings and stable references to raw receipts; retrieve exact evidence only when integration or judgment needs it. Files, implementation batches, plan steps, and intermediate drafts are not deliverables. Merge adjacent outputs before the next dependency or commitment boundary. During production, run targeted checks mapped to changed predicates. When artifact state and write permissions permit, independent deterministic closure such as consumer audit, architecture-document reachability, projection freshness, runtime smoke, and test shards may run concurrently and join once. Broaden to full regression only when the actual impact surface or dependency uncertainty requires it. Where the workspace maintains a behavior-assertion registry for its user-visible surfaces, run the registered executable carriers — end-to-end included — of every surface the delivery touched after integration and before Manager acceptance; a red carrier is repaired in-task through the repair-now route. Capture an independent candidate-state list only when drift risk across repositories, runtimes, artifacts, concurrent writers, or a long wait makes the observed state otherwise ambiguous. Neither is a fixed closeout step.

Evidence is assigned, preserved, and reminted per predicate under [evidence.md](evidence.md). When independent semantic judgment is warranted, identify one locked commitment identity and exact state, then select one verifier or a parallel wave divided by real specialist capability, observation method, or model blind spot. Join the initial review, then close repairs through affected predicates' true judges. Resolved parts are not replayed without invalidation. A materially new commitment gets a fresh verifier-need assessment. Unknown remains open until settled, judged unjudgeable under [Predicate closure](evidence.md#predicate-closure), or returned to Direction when its bounds change.

## Governed changes

Before adding, changing, or removing a rule, default, or constraint, read the Human-Agent Principles and the applicable project Vision through its project entry. Collaboration-method mechanisms derive from the Vision of the project that owns the method; an affected project's product commitments retain that project's own authority. Use the `writing-for-agents` skill, if installed, for agent-consumed instructions. Reuse current context and existing execution authority.

Derive the protected outcome from those foundations, with current evidence as the reference that tests it. Distinguish a durable requirement from a conditional method or a patch for an observed capability gap. Apply P3 to necessity and scope: explain the observed gap, why existing or simpler means are insufficient, and which conditions make the method useful. A real simpler sufficient case narrows a proposed universal method. Within settled bounds an executing agent may choose an alternative supported by qualified evidence of the same protection; confidence, lower cost, or a model announcement alone does not establish equivalence. Keep material rationale in the existing task or result, without a separate admission form.

A temporary capability patch names its observed gap, outcome probe, review point or expiry, executable exit action, and the protected requirement that survives removal. At that point, use the evidence to keep, narrow, replace, or remove the patch. Insufficient evidence names the missing observation and next bounded trigger; expiry alone never drops a required protection. Use the existing task or observation record rather than creating a separate patch registry or scheduler.

Locate the decisions and consumers affected by the rule. Establish how each receives the authority before its decision, following the directive contract above. Remove or narrow superseded current clauses and competing carriers in the same candidate; preserve historical references as clearly labeled pointers where needed. Assign changed or unproven loading and application predicates through [evidence.md](evidence.md), reusing still-valid evidence. A canonical file, link, generated profile, or syntax pass alone does not prove runtime activation or correct application; unobserved paths remain unknown. If the project defines an improvement or learning method, read its applicable branch before choosing a change to that method.

Use qualified independent judgment (the `verifier` agent) for semantic scope, conflicts, necessity, and equivalent revivals. Machine checks enforce formalized schema, enums, paths, structure, transitions, reachability, and state binding; prose classifiers, regex, embeddings, and automated LLM scores do not establish semantic equivalence, completeness, or quality. User-owned foundation changes remain under P1.

## Review presentation

Before Manager requests judgment on any concrete review object, present that exact object in a form the user can open in their current client, including during remote control. Choose the simplest available carrier sufficient for that judgment. When interaction affects the decision, the user must be able to perform it in the presented object. A host-only file path, localhost URL, or desktop panel does not establish remote access; source code alone does not present a rendered UI. Where the object includes a surface that already exists, its rendering derives from that surface's own styles and structure; an approximation reconstructed from description is a different object, and approval of it does not carry to the real surface. The presentation identifies its exact durable or version-bound source, and approval binds to that source object and version. Establish that the carrier is accessible in the current client, reusing still-current capability evidence. If it is inaccessible, choose an accessible equivalent within existing authority; if none is available, the review gate remains open. Changing carriers does not expand publishing, audience, data-sharing, or product-release authority. Runtime bindings map available mechanisms to these requirements.

The review page carries only what can change the user's next choice: the object rendered at the viewport of the device they review on, each open decision, and any consequence that would change that decision. An open decision is one the user owns that no source under [Frontier admission](direction.md#grill) settles; a settled decision shows only inside the object, and a proposal without current value is dropped rather than asked. Candidates differ in rendered form, switched in the same place, with text only for a consequence rendering cannot show. Rationale, evidence, process, settled decisions, and rejected alternatives stay off the page; the task record and repository artifacts are their record. This ceiling bounds the page presented for judgment; what a source-local standard records inside its own repository artifact is unaffected.

A periodic review's concise conversational outcome commitment may itself be the review object, with rendered chat as its carrier.

## Followup closure

### Architecture impact

Treat the initial architecture-impact call as provisional. Before completion, compare the final integrated candidate with live authority and the project's documentation routing rules. When the candidate changes stable container or domain topology, semantic authority or state ownership — including rules, roles, lifecycle, or evidence — a trust invariant, or a durable decision, update the project's owning architecture document in the same candidate. When the changed fact fails that document's admission, leave one concise disposition with the pull request or delivery summary that names the admission reason or current owner. Add no task-record field, routine progress write, parallel architecture record, or implementation-detail summary for this disposition.

Machines may verify the architecture entry, structure, links, and reachability; a qualified reader judges whether the final candidate's semantic impact is sufficiently represented. A structural pass cannot close that judgment.

### Followup routing

If the project defines an improvement or learning method, read its branch for learning records before deciding which findings to retain. Research disposition and executable followup are separate; the routes below govern execution, not deletion of useful learning.

Before completion, reconcile the locked Intent, final delivery, qualified findings, user corrections, explicit deferred or out-of-scope work, and material downstream effects against current evidence. Inspect execution events when their observed impact, recurrence, or unresolved outcome could change acceptance, recovery, or a worthwhile improvement: significant failures, repeated retries or corrections, costly waits, handoffs, and context loss. Use existing records and deepen a trace only for a concrete question. Preserve material incidents and report missing observations when they limit a claim. Route each supported material delta exactly once:

1. **Repair now** when current Acceptance remains open; an unjudgeable predicate is not open work for this route.
2. **Reopen Direction** when Goal, Boundary, Approach, or Acceptance must change.
3. **Continue-now candidate** when work is valuable and outside the locked Acceptance and no concrete blocker prevents starting it now. This task's Intent stays as locked.
4. **Blocked candidate** when work is valuable and outside the locked Acceptance but a concrete blocker prevents starting it now; the candidate names that blocker.
5. **Discard** when evidence or expected value does not justify user attention.

An execution-process delta becomes a candidate only when observation shows actual rework, delay, or risk, a plausible recurrence gap, and independently valuable improvement; each candidate states that evidence, cost, recurrence rationale, and smallest viable improvement. Discard one-off mistakes, transient faults with no material cost, fully fixed faults with no recurrence gap, issues already covered by an existing task record, and speculative best practices. A fault counts as fully fixed only when the fix landed at the layer where recurrence would occur — an in-task workaround leaves the cross-session gap open.

For routes 3 and 4, first check a standing delivery mandate the project records, if any. Work covered by an effective mandate is already authorized: cite its scope fit and apply the defaults below within its bounds. Other candidates go to the user for selection; Manager chooses the route from the concrete blocker and never invents authorization. When the executable candidate set is empty, state "Followup: none" in the user's language. Only candidates needing user selection make closeout blocking: number them, state their value and why they are outside current Acceptance (plus the blocker for route 4), and present delivered-outcome judgment separately from selection through the runtime's native user-question tool; "needs adjustment" reruns the sweep after repair. Unselected candidates create no task, ownership, or scheduled obligation; useful hypotheses and evidence may remain in the project's research record, which grants no execution authority.

Selected candidates follow fixed defaults, without re-presenting the disposition:

1. **No blocker: continue now.** Every selected candidate with no concrete blocker merges into one continuation, delivered by this same Manager in this conversation in the same turn; when the project keeps task records, create it as a parent-linked record already owned by this conversation. Pacing of authorized work is execution-owned; a turn ends only at a user-owned choice, a real blocker, a bounded external wait, or completion.
2. **Blocked: queue.** Every selected candidate a concrete blocker prevents starting now is recorded with its blocker in the project's queue, if one exists, otherwise reported. When the blocker is that only later real use can produce the evidence, record it as an observation (see [Predicate closure](evidence.md#predicate-closure)).
3. **Deferred only on instruction.** A candidate is parked without a start condition only when the user explicitly directs it; Manager never defers on its own initiative.

At terminal closure, retain a concise micro-retro for material rework, delay, user corrections, or failed continuation: observed effect, evidence reference, attempted remedy, and any unresolved recurrence gap. Distinguish observed absence from unavailable process evidence; preserve this factual feedback even when no followup is selected. Detailed traces stay at their source.
